# 0013 — Stream answers and ingest progress over SSE; cancel on disconnect

Answers stream from `POST /sessions/:id/messages/stream` and ingest progress from `GET /repos/:id/events`, both as Server-Sent Events. The event types (`ChatStreamEvent`, `RepoProgressEvent`) live in `@cda/domain/events`, a file with no imports that the web app imports type-only.

**SSE over WebSockets.** Both streams flow one way, server to browser, and are tied to one request. SSE is plain HTTP: it passes CORS and proxies like any request, needs no extra server or protocol, and reconnects by itself (`EventSource`, used for repo progress). Answers need a POST body, so the browser reads that stream with `fetch` and a small parser instead of `EventSource`. WebSockets would add a second protocol and connection handling for no two-way need.

**Cancel on disconnect, rather than finishing in the background.** When the client goes away mid-answer, the request's `AbortSignal` aborts the in-flight Claude call and no further iteration starts. The answer is stored as a short "cancelled" message, so the session stays a clean question/answer sequence and the next question works normally. The aborted call is logged in `llm_calls` as `failed`. Finishing in the background would keep spending tokens on an answer nobody is waiting for. The trade-off is that a reload during an answer loses it, and the user must ask again.

**Ingest progress: Redis pub/sub, snapshots, one shared subscriber.** The ingest worker publishes a full snapshot (status, files and chunks so far) to `repo-progress:<repoId>` after each stored file and at every status change. Snapshots rather than deltas mean a client that misses events only needs the next one. `GET /repos/:id/events` subscribes before reading the current state from Postgres, so nothing falls between the two, and closes the stream after `ready` or `failed`. One Redis subscriber connection per API process fans out to all open streams; a channel is subscribed while it has listeners and unsubscribed when its last listener leaves. Pub/sub is fire-and-forget, which suits progress: publishing never blocks or fails an ingest, and the authoritative state stays in Postgres. Closing a progress stream never touches the BullMQ job.

**Shared types, type-only.** The web app imports `@cda/domain/events` with `import type`, so no domain code (and none of its Node dependencies) is bundled, and a fresh clone needs no domain build before `next dev`. The one runtime helper the web needs, "is this status final", is a one-line copy.
