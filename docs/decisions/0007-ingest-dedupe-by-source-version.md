# 0007 — Deduplicate ingests by source version, not by repo URL

Each ingest is identified by `ingest_key` = sha256(`git:<normalised url>@<commit sha>`) for GitHub sources, or sha256(`local:<sha256 of the zip>`) for uploads. `repos.ingest_key` is unique, and the same key is the BullMQ `jobId`. We chose this over one row per URL, which would be re-ingested in place. Pinning to an exact commit or content makes "re-submit the same source" a cheap no-op (`200`, `deduplicated: true`) without cloning or embedding anything. Two concurrent submissions resolve to one row through the unique constraint. Every row describes exactly one immutable snapshot, which later citations can rely on. The commit is resolved with `git ls-remote` before enqueueing, and the job fetches that exact SHA (depth 1) rather than "whatever HEAD is now". A push between submit and processing therefore cannot change what gets indexed. The cost is that a new commit creates a new repo row. Re-submitting a source whose ingest failed puts the same row back in the queue. Jobs are removed from Redis when they finish, so the jobId is free for that retry, and the outcome lives in Postgres (`repos`, `ingest_jobs`).
